# MCP 2026-07-28 support

OpenChrome serves the stateless MCP `2026-07-28` revision alongside legacy
(initialize-based) MCP clients. This page records what is supported on each
transport, how OpenChrome keeps browser state explicit, and what remains
out of scope.

Primary references:

- [MCP 2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28)
- [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- [Versioning and dual-era servers](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)

## Architecture

The official MCP TypeScript SDK (`@modelcontextprotocol/server` and
`@modelcontextprotocol/node` 2.x) owns the protocol boundary for modern
requests and for stdio. OpenChrome's `MCPServer` remains the application
runtime for browser sessions, tools, resources, authorization, rate limiting
and observability.

```text
MCP client
    |
    | stdio (both eras) or Streamable HTTP
    v
official MCP SDK                      legacy HTTP path (sessionful)
  - era selection                       - initialize / Mcp-Session-Id
  - envelope + header validation        - GET/SSE notifications, DELETE
  - server/discover, cache hints        - server->client requests on SSE
  - subscriptions/listen, MRTR
    |                                         |
    v                                         v
OpenChrome SDK adapter  ------------->  OpenChrome MCPServer core
  - per-request era, client info,         - explicit sessionId/tabId state
    capabilities, principal, tenant       - tools, resources, policy, CDP
  - request/notify/log bridges            - per-client message delivery
```

Every server-originated message (progress, logging, list changes,
server->client requests) is delivered only to the client whose request
produced it. HTTP requests that carry no MCP session receive none of them.

## Protocol support per transport

The runtime contract advertised in `capabilities.experimental["io.openchrome/runtime"]`
(initialize and `server/discover`) reports the same values.

| Transport | Legacy clients | Modern clients |
| --- | --- | --- |
| stdio | `initialize`; version negotiated by the SDK (2024-10-07 through 2025-11-25) | `server/discover` or any request with the modern envelope |
| HTTP | `initialize` returns `2024-11-05`; `Mcp-Session-Id`, GET/SSE and DELETE | Stateless POST with `MCP-Protocol-Version: 2026-07-28`, `Mcp-Method`, `Mcp-Name` |
| `both` | Each transport negotiates independently | Each transport negotiates independently |

On the legacy HTTP path a request may omit `MCP-Protocol-Version` or send
`2024-11-05`; any other value is rejected with `-32600` naming the supported
versions. Modern HTTP requests never mint, echo or honour `Mcp-Session-Id`,
and modern `GET`/`DELETE` are rejected.

## Browser state model

The protocol is stateless; Chrome is not. Protocol context (version,
capabilities, client identity, log level) is read from each request.
Application state lives in the browser runtime and is referenced by explicit
identifiers:

- the stdio peer is the local client and keeps the historical `default`
  browser session;
- legacy HTTP clients get one browser session per `Mcp-Session-Id`;
- `sessionId` and `tabId` tool arguments address browser state explicitly.

Removing the MCP session does not make browser state portable across
daemons: a browser session belongs to one OpenChrome process and its Chrome.

## Tool discovery

Legacy clients keep progressive disclosure (`expand_tools` plus
`tools/list_changed`) when they support list-change notifications.

Modern `tools/list` must not vary per connection or as a side effect of other
requests, so it always returns the complete registry filtered only by the
server's capability configuration and the caller's authorization scopes, in
a deterministic order, with a private cache hint.

## Cache hints

| Method | `ttlMs` | Scope | Reason |
| --- | ---: | --- | --- |
| `server/discover` | 300000 | public | Product identity and protocol capabilities are stable |
| `tools/list` | 30000 | private | Tool visibility depends on authorization |
| `resources/list` | 0 | private | Live browser sessions change frequently |
| `resources/templates/list` | 60000 | private | Templates are stable but deployment-specific |
| `resources/read` | 0 | private | Live browser state must not be reused |

## Server-to-client input (MRTR)

Modern MCP does not allow an OpenChrome tool to push a JSON-RPC request to
the client. The SDK adapter converts the existing calls:

| Existing call | Modern input request |
| --- | --- |
| `elicitation/create` | Form or URL elicitation in `inputRequests` |
| `sampling/createMessage` | Sampling request in `inputRequests` |
| `roots/list` | Roots request in `inputRequests` |

The first `tools/call` returns `resultType: "input_required"`; the client
retries the original call with a new JSON-RPC id and matching
`inputResponses`. Tools re-run from their original arguments. Tools that ask
for input do so before any browser side effect.

Roots and Sampling are deprecated in 2026-07-28. Modern URL and file-output
tools request roots before egress and enforce the returned roots for that
request only; they are never cached across requests.

## Cancellation

- stdio (both eras, served by the SDK) and modern HTTP: a cancelled request
  gets no response, as the MCP specification asks (`notifications/cancelled`
  on stdio; closing the response stream on modern HTTP). The tool is stopped
  cooperatively; CDP commands already sent are not rolled back, so the client
  must re-observe the page before repeating the action.
- Legacy HTTP (sessionful): a cancelled call still answers with
  `execution: "unknown"` and `retryAllowed: false`.

Before this release, stdio clients received that `execution: "unknown"`
answer after cancelling; now they receive nothing, which the spec requires
for 2026-07-28 and recommends for earlier revisions.

## Subscriptions

Modern clients open `subscriptions/listen` and choose `toolsListChanged`,
`resourcesListChanged` and/or `resourceSubscriptions`. The SDK acknowledges
the subscription first and tags every event with its subscription id. On
HTTP, resource events are published only to streams opened by the tenant
that owns the resource; unresolved ownership publishes nothing.

Legacy `resources/subscribe`, `resources/unsubscribe`, `GET /mcp` and
`GET /mcp/sse` remain on the legacy path. A legacy HTTP request without an
`Mcp-Session-Id` cannot subscribe because it has no notification stream.

## Security

- Bearer, API-key, JWT, tenant, CORS and loopback checks run before SDK
  dispatch. Only the authenticated principal and normalized tenant and
  broker identifiers enter the SDK request context; credentials never do.
- Modern routing headers are validated against the JSON-RPC body before
  dispatch (`-32020`); a missing required capability returns `-32021`; an
  unsupported version returns `-32022`.
- Browser CORS allows and exposes `MCP-Protocol-Version`, `Mcp-Method` and
  `Mcp-Name`.
- `tools/list` hides tools the caller's scopes cannot call.

## Runtime and upgrades

OpenChrome requires Node.js 20 or newer (SDK 2.x requirement).

Installing a new package does not replace a running server. Restart the
server, reconnect the host and rediscover tools. Compare the running
`runtimeId` and `packageVersion` from initialize or `server/discover` with
the ones you saw before; a changed `runtimeId` means every previously held
`sessionId`, `tabId` or lease must be re-acquired, and a request that names
the old runtime in `_meta["io.openchrome/runtimeId"]` is rejected with
`STALE_RUNTIME` before any browser action.
